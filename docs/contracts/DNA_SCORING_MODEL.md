# DNA_SCORING_MODEL.md
# DNA Scoring Model Contract

**Version:** 1.0.0
**Status:** CANONICAL
**Last Updated:** 2026-03-08

---

## 1. Purpose

This contract defines the canonical scoring model for bet and parlay evaluation in DNA Matrix / BetApp.

The scoring model exists to answer one product question:

> "Is this bet structurally solid or am I fooling myself?"

The model is deterministic, explainable, and auditable. It does NOT predict guaranteed outcomes and MUST NOT present itself as a picks engine.

### 1.1 Product Intent

The scoring model MUST help users:

- identify hidden structural risk
- compress messy research into faster decisions
- learn why bets are strong or fragile over time

### 1.2 Non-Goals

This contract does NOT:

- guarantee winning bets
- authorize black-box scoring
- permit silent bet modification
- define sport-specific feature engineering in full detail

---

## 2. Core Philosophy

DNA evaluates probability context and structural risk, not certainty.

```
Probability intelligence
+ Structural risk detection
+ Contextual heuristics
= DNA evaluation
```

The system MUST say:

> "This bet is structurally strong or weak for these reasons."

The system MUST NOT say:

> "This bet will win."

---

## 3. Canonical Outputs

Every evaluation MUST produce these four canonical scores:

| Score | Range | Meaning |
|-------|-------|---------|
| `confidence` | 0-100 | Structural soundness |
| `fragility` | 0-100 | Risk stacking severity |
| `edge` | -100 to +100 | Market advantage estimate |
| `stability` | 0-100 | Environmental stability |

These four scores are the canonical numeric output of DNA v1.

### 3.1 Badge Mapping

User-facing confidence badges MUST map as follows:

| Confidence | Badge |
|------------|-------|
| `85-100` | `green` |
| `70-84` | `yellow` |
| `55-69` | `orange` |
| `0-54` | `red` |

**Policy:** Green MUST remain scarce. The system SHOULD avoid overproducing high-confidence verdicts.

---

## 4. Signal Groups

The scoring model uses four signal groups:

1. Market Signals
2. Statistical Signals
3. Structural Signals
4. Context Signals

### 4.1 Market Signals

Market signals are derived from sportsbook or market data.

Examples:

- implied probability
- line movement
- book disagreement
- price/value context

### 4.2 Statistical Signals

Statistical signals are derived from team or player performance data.

Examples:

- offensive and defensive ratings
- matchup advantage
- recent form
- usage and role metrics

### 4.3 Structural Signals

Structural signals model slip shape, especially for parlays.

Examples:

- leg count
- correlation between legs
- variance stacking
- bet-type volatility

### 4.4 Context Signals

Context signals are generated by protocols and heuristics.

Examples:

- fatigue
- travel stress
- lineup instability
- pace mismatch
- officiating tendencies

**Invariant:** Context signals MUST modify `stability` and/or `fragility`. They MUST NOT silently overwrite the baseline probability model.

---

## 5. Evaluation Pipeline

All scoring implementations MUST conceptually follow this pipeline:

```
Input Bet
  -> Market Normalization
  -> Statistical Probability Model
  -> Structural Risk Analysis
  -> Protocol Context Analysis
  -> Score Aggregation
  -> Sherlock Explanation
```

### 5.1 Stage Intent

| Stage | Purpose |
|-------|---------|
| Market Normalization | Convert market data into comparable probability context |
| Statistical Probability Model | Estimate baseline model probability per leg |
| Structural Risk Analysis | Measure parlay shape, correlation, and variance stacking |
| Protocol Context Analysis | Apply schedule, lineup, fatigue, and environment modifiers |
| Score Aggregation | Produce canonical output scores |
| Sherlock Explanation | Explain score drivers in human-readable form |

---

## 6. Baseline Probability Model

Each leg MUST produce a `model_probability`.

Example form:

```
P = sigmoid(
  w1 * offense_advantage
+ w2 * defense_advantage
+ w3 * matchup_history
+ w4 * home_court
+ w5 * injury_adjustment
)
```

This formula is illustrative, not binding at the feature level.

### 6.1 Binding Requirements

- each leg MUST produce a bounded probability estimate
- probability estimation MUST be deterministic for the same inputs
- feature weights and transformations MUST be versioned
- missing data handling MUST be explicit, not silent

---

## 7. Parlay Probability

For independent legs:

```
P_parlay = product(P_leg)
```

Because real parlays are not independent, the model MUST apply a correlation penalty.

Illustrative form:

```
AdjustedProbability = product(P_leg) * CorrelationModifier
CorrelationModifier = 1 - correlationRisk
```

### 7.1 Binding Requirements

- multi-leg evaluations MUST account for correlation explicitly
- correlation handling MUST be visible in explanation output for qualifying tiers
- same-game or tightly linked legs SHOULD receive stronger penalties than loosely related legs

---

## 8. Fragility Score

`fragility` measures how easily a slip breaks due to stacked risk.

Illustrative structure:

```
Fragility =
  LegCountFactor
+ CorrelationFactor
+ VarianceFactor
+ ProtocolRiskFactor
```

Illustrative example:

```
Fragility =
  10
+ (8 * legs)
+ correlationPenalty
+ volatilityPenalty
+ protocolPenalty
```

Then normalized to:

```
0-100
```

### 8.1 Binding Requirements

- fragility MUST increase with leg count unless explicitly offset by other factors
- fragility MUST penalize correlated structures
- fragility MUST remain visible in every evaluation tier
- fragility MUST never be hidden behind a single confidence number

---

## 9. Stability Score

`stability` measures the reliability of the betting environment.

Illustrative structure:

```
Stability =
  100
- fatiguePenalty
- injuryPenalty
- lineupVolatility
- officiatingVariance
```

### 9.1 Binding Requirements

- stability MUST be bounded to `0-100`
- protocol and heuristic signals SHOULD primarily affect stability
- stability reductions MUST be explainable in user-facing output

---

## 10. Edge Score

`edge` compares model probability to market-implied probability.

Illustrative form:

```
MarketProbability = implied odds probability
Edge = (ModelProbability - MarketProbability) * 100
```

### 10.1 Edge Interpretation

| Edge | Meaning |
|------|---------|
| `> +5` | strong value |
| `+2 to +5` | modest edge |
| `-2 to +2` | neutral |
| `< -2` | overpriced |

### 10.2 Binding Requirements

- edge MUST preserve sign
- edge MUST use normalized market probability
- edge MAY be computed per leg and/or for the full slip, but scope MUST be explicit

---

## 11. Final Confidence Score

`confidence` combines probability quality, environment, value, and fragility.

Illustrative v1 weighting:

```
Confidence =
  40% ProbabilityStrength
+ 25% Stability
+ 20% Edge
- 15% Fragility
```

Final value MUST be clamped to:

```
0-100
```

### 11.1 Binding Requirements

- confidence MUST be a derived score, not a manually assigned label
- confidence MUST decrease when fragility materially rises
- confidence MUST reflect uncertainty rather than mask it
- confidence MUST remain calibrated over time against observed outcomes

---

## 12. Protocol Modifiers

Protocols provide contextual penalties or adjustments.

Illustrative examples:

| Protocol | Example Effect |
|----------|----------------|
| Back-to-back fatigue | `-8 stability` |
| Travel stress | `-5 stability` |
| Lineup instability | `+7 fragility` |
| Pace mismatch | `+4 volatility` |

### 12.1 Binding Requirements

- protocol effects MUST be explicit and loggable
- protocol weights MUST be tunable via a registry or equivalent configuration layer
- protocol modifiers MUST not mutate the input bet
- protocol modifiers MUST be explainable to the user at supported tiers

---

## 13. Recommendation Logic

Recommendation output MUST use:

- `confidence`
- `fragility`
- `edge`
- user risk profile when available

Allowed v1 recommendation classes:

- `proceed`
- `proceed_with_caution`
- `consider_simplifying`
- `avoid_fragile_structure`

### 13.1 Binding Requirements

- recommendation MUST inform, not block
- recommendation MUST be traceable to score drivers
- recommendation language MUST not imply certainty

---

## 14. Analysis Tiers

`GOOD`, `BETTER`, and `BEST` describe analysis depth, not bet quality.

### 14.1 GOOD

MUST include:

- probability estimate
- fragility score
- basic Sherlock summary

### 14.2 BETTER

MUST add:

- protocol analysis
- deeper reasoning
- volatility explanation
- recommendation suggestions

### 14.3 BEST

MUST add:

- full protocol set
- correlation analysis
- strategy fit analysis
- advanced recommendations

**Invariant:** Tier labels MUST NEVER be interpreted as "good bet / better bet / best bet."

---

## 15. Explanation Contract

Every evaluation MUST provide a human-readable explanation payload.

Minimum explanation shape:

```json
{
  "confidence_label": "Moderate",
  "strengths": [
    "Favorable offensive matchup",
    "Slight market edge (+3%)"
  ],
  "risks": [
    "Parlay contains 5 legs",
    "Pace mismatch introduces volatility"
  ],
  "recommendation": "Consider reducing to 3-4 legs for improved stability."
}
```

### 15.1 Binding Requirements

- explanations MUST state why the score exists
- explanations MUST surface both strengths and risks
- explanations MUST avoid black-box language
- explanations MUST not imply guaranteed outcome

---

## 16. Logging Contract

Every evaluation MUST log enough detail for audit and calibration.

Minimum logged fields:

- input slip
- normalized market inputs
- model probability
- fragility
- stability
- edge
- triggered protocols
- final confidence
- recommendation
- score model version

### 16.1 Purpose

Logging enables:

- accuracy tracking
- protocol tuning
- score calibration
- explanation debugging

---

## 17. Calibration Requirements

The system MUST support confidence calibration over time.

Minimum calibration requirement:

```
confidence_bucket -> expected outcome rate vs actual outcome rate
```

Illustrative table:

| Confidence Bucket | Expected Win % | Actual Win % |
|-------------------|----------------|--------------|
| `70-75` | `72` | `69` |
| `75-80` | `78` | `80` |

### 17.1 Binding Requirements

- score outputs MUST be loggable by confidence bucket
- later calibration work MUST compare expected vs actual outcomes
- score changes SHOULD be versioned to avoid mixing incompatible eras

---

## 18. Guardrails

The scoring model MUST obey these rules:

### 18.1 No Win Guarantees

The system MUST never present scores as certainty or promise.

### 18.2 No Hidden Uncertainty

Fragility and other uncertainty signals MUST remain visible.

### 18.3 No Black-Box Outputs

Every score MUST have an explanation path.

### 18.4 No Silent Bet Mutation

The system MAY suggest reshaping a bet but MUST NOT silently alter it.

---

## 19. Product Positioning Implication

This model is different from simple stats or odds dashboards because it explicitly evaluates:

- structural risk
- variance stacking
- contextual volatility

It SHOULD behave more like risk modeling than picks marketing.

---

## 20. Future Expansion

Out of scope for v1, but compatible with this contract:

- player-level predictive models
- real-time protocol triggers
- simulation engines
- bet portfolio optimization

These future capabilities MUST preserve the v1 guardrails around explainability and uncertainty.
